## Kept items

### 1. Reverse engineer skills from examples instead of writing them
[Stop Writing Claude Skills. Reverse Engineer Them](https://www.youtube.com/watch?v=57FpQnLTEBY) (Ben AI, Oct 16, 9 min, transcript read)

**What it is:** A three-step method for building a skill: gather best and worst real outputs, have Claude find the patterns that separate them, then have it build the skill from those patterns.
**Why it matters:** Ben says his newsletter skill built from 6 best and 6 worst newsletters beat the one he wrote by describing the process. His key prompt line tags every finding as seen, inferred or unknown so Claude does not invent reasons.
**Suggested change:** `skills/personal-voice/SKILL.md`: rebuild or check it against a set of Matt's best and worst real sent emails, with findings tagged seen/inferred/unknown, before the next rewrite of the voice rules.
**Client angle:** Show a model the three best proposals or reports and have it derive the template, rather than describing the template.

### 2. Cache clock and handoff mods
[I Tried 100+ Claude Mods, These 9 Are the Best](https://www.youtube.com/watch?v=bTqizdva04g) (Ben AI, Oct 21, 14 min, transcript read)

**What it is:** Mods are Claude Code plugins that listen for events (prompt sent, tool call, reply finished) and can watch, change or block them. Two stand out: a countdown for when a chat's prompt cache goes cold, and a handoff that writes a detailed prompt for a fresh chat at 250k tokens or when the cache goes cold.
**Why it matters:** Ben claims a cold-cache return to a long Opus 5.5 chat costs about $1.6 versus 4 cents warm, with a 1 hour timer on a subscription. Those figures are from the video and unverified. This matches Matt's token-cost rule and the "offer a handoff" line in his CLAUDE.md.
**Suggested change:** `claude/CLAUDE.md`, section "Reversals and long sessions": add a long-session trigger (about 250k tokens or a cold cache) beside the midnight and two-reversals triggers. A mod would be a new automation, so it needs `karpathy-structural-review` first.

### 3. Adversarial review over-engineers
[Redesigning source control at Anthropic](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/) (Simon Willison, Oct 13, quoting the [Anthropic engineering post](https://www.anthropic.com/engineering))

**What it is:** Anthropic replaced Git with an in-house system (Scion) after merges rose from about 2,500 to over 30,000 a day, built by 7 people in 5 months.
**Why it matters:** The post says adversarial review is very effective but can be myopic, and engineers had to steer Claude away from over-engineering in response to hypothetical concerns. Simon reports the same from playing Claude and GPT against each other.
**Suggested change:** `agents/karpathy-structural-review.md`: add a line that a concern needs a real, current cause to count, so the review agent does not invent hypothetical risks (inferred fit, not stated by the source).
**Client angle:** When using a second model to review work, require each objection to cite something concrete.

### 4. Ask which check fits the risk, not whether a human read it
[Quoting Addy Osmani, Morgan Westlee Lunt, and Qing Wang](https://simonwillison.net/2026/Oct/16/code-review/) (Simon Willison, Oct 16)

**What it is:** The Claude Code team's review approach: replace "did a human read it" with "what could go wrong, and which check, automated or human, catches it". Review runs continuously, and Claude reviews most changes before a human does.
**Why it matters:** It moves review from a gate at the end to a running check. Matt's rule sends every risky change to a human yes, which is the gate model (inferred comparison).
**Suggested change:** `claude/CLAUDE.md`, "Risky changes" paragraph: consider naming the specific check per change type (for example an agent review for hooks) instead of one blanket human yes. Matt's call, since it loosens an approval rule.
**Client angle:** Define the failure to guard against first, then pick the check.
